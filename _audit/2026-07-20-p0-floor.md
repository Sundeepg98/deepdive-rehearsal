### 2. `debugging` — `IS DISTINCT FROM` offered as a fix for the wrong population

| | |
|---|---|
| **Panes** | Drill SDE2 (l.133) + Senior (l.141), Whiteboard (l.591 — feeds the cram spine) |
| **Offending** | "The fix is `col = 'value' OR col IS NULL`, or `col IS DISTINCT FROM ...`" |
| **Corrected** | the operator dropped from the inclusion list; the two traps now stated as a pair |
| **Receipt** | offending 0/0 · `IS DISTINCT FROM` fixes only the second` 1/1 |

Verified the reader's analysis independently and it is exactly right. `col IS DISTINCT FROM 'value'`
returns `{col <> 'value'} ∪ {NULL}` — the *opposite* population from the include-filter it was
offered to fix. And there is no `IS [NOT] DISTINCT FROM` form that works here: `col IS NOT DISTINCT
FROM 'value'` is null-safe equality, and since `'value'` is not NULL, a NULL row evaluates FALSE, so
it excludes NULLs too.

I took the reader's stronger suggestion and stated both traps as a pair (`=` drops NULLs from an
*include* filter → `OR col IS NULL`; `<>` drops them from an *exclude* filter → `IS DISTINCT FROM`),
which converts an error into a distinction that earns signal.

**Beyond the finding.** The Senior line (l.141) said "reaching for `IS DISTINCT FROM`… is the
forensics tell" without saying *which* trap it solves. The reader did not list it, but once the main
answer is corrected that line reads as endorsing the error, so I made it name the pair. The `Follow`
at l.139 was already correct ("everything except value, NULLs included") and is untouched.
Confirmed by grep that `IS DISTINCT FROM` appears nowhere else in `src/` or `tools/`, so the cram
sheet is fed only from the Whiteboard site that was fixed.

### 7. `saga` — a comment claiming a guard the SQL did not have

| | |
|---|---|
| **Pane** | Walk step 5, "Make every step and every compensation idempotent" |

```sql
UPDATE inventory SET available = available - 1

```

### 9. `autoscaling` — the crash-loop amplifier inverted

| | |
|---|---|
| **Panes** | Bank CURVEBALL crash-loop amplifier (l.1049) + Staff drill item (4) (l.413) |
| **Offending** | "crash-looping pods … contribute no useful capacity, so **all** the real load is concentrated on the few **healthy** pods"; "**failure inflates the scaling signal**" |
| **Corrected** | the guard named first, then the scenario re-anchored on a fleet-level signal |
| **Receipt** | both offending 0/0 · `assuming 0% consumption` 1/1 · `the direction **reverses**` 1/1 |

Checked against the documented HPA algorithm and the reader is right. For resource metrics,
not-yet-Ready pods are **set aside**, the ratio is computed on ready pods, and then — on a would-be
scale-up — the not-ready pods are **added back assuming 0% consumption**, specifically to dampen
this. If the recomputed ratio reverses direction or falls within tolerance, scaling is skipped. At
the card's own numbers (10 replicas, 5 crash-looping, 5 at 100%, target 70%): ready-only ratio
1.43 → recomputed `(5×100 + 5×0)/10` = 50% → 0.71 → direction reverses → the controller returns
`currentReplicas` and does nothing. The march to 60 pods does not happen from a stock CPU HPA.

Rewrote so the card *leads* with the guard (it is the sharpest fact available and it is what a
Kubernetes-deep interviewer is testing), then re-anchors on **queue depth / ingress RPS / any
Object or External metric — what a KEDA scaler reads**. Those are fleet-level numbers with no
per-pod readiness to set aside, so the dampening never applies and the runaway is real. Also noted
the CPU case where it *does* happen: pods that pass readiness and crash afterwards are counted Ready.

**Beyond the finding.** Queue depth was chosen deliberately over ingress RPS as the primary
re-anchor, because it keeps the card's punchline literally true: a crash-looping fleet drains
nothing, so the queue genuinely rises **because** of the failure. The meta-guard (4) now reads
"queue depth rises precisely because pods are failing to drain it", and I added the contrast the
reader noted sits awkwardly in the same pane — on CPU the same fleet would have *deflated* the
signal and the readiness guard would have dampened it further. The two halves of the pane no longer
fight; "which metric" is now the explicit lesson.

| **Offending** | "add a `parent_deleted_at` column on the child and make the FK composite against `(parent_id, parent_deleted_at)` --- so a reference is only valid against a live parent" |
| **Corrected** | the nullable version named as a no-op; a NOT NULL liveness mirror that actually enforces |
| **Receipt** | offending 0/0 · `MATCH SIMPLE` 5/5 · `is_live boolean NOT NULL` 4/4 |

With the topic's own nullable `deleted_at`, a live parent means the child stores
`parent_deleted_at = NULL` — and under **MATCH SIMPLE** (the default in Postgres and the only
semantics MySQL implements) a foreign key with **any** NULL column is not checked at all. So the
composite FK is a no-op for exactly the live-parent case it claims to enforce: you could insert
`(product_id = 99999, NULL)` against a nonexistent product and it passes. It is *strictly weaker*
than the plain FK it replaced, because it stopped guaranteeing even existence. MATCH FULL does not
rescue it — one-null-one-not raises an error, so every live reference would be rejected.

**Beyond the finding — a different fix from the reader's.** The reader proposed a NOT NULL liveness
mirror with `ON UPDATE CASCADE`. I kept the NOT NULL mirror (that part is the key insight) but
dropped the cascade, because the simpler construction is both correct and stronger:

```sql
parent: is_live boolean NOT NULL, UNIQUE (id, is_live)
child:  parent_is_live boolean NOT NULL CHECK (parent_is_live),
        FOREIGN KEY (parent_id, parent_is_live) REFERENCES parent (id, is_live)
```

Every column is populated, so the constraint is always checked. Soft-deleting a parent flips
`is_live` to false; any child still referencing `(id, true)` now has no target, so the parent's
update is **rejected**. That is `RESTRICT` — one of the three policies the topic already names —
enforced by the database rather than remembered by a developer, and it needs no cascade at all.
With `ON UPDATE CASCADE` you would need the `CHECK` to bounce the cascaded write to get the same
outcome, which is the same result by a longer road. The honest cost is that the decision is forced
at delete time, which the corrected text states, and the "prevention traded for detection" fallback
the pane closes on is preserved for teams that do not want that.

This also reinforces rather than contradicts the NULL lesson the topic teaches three cards earlier
(`soft-delete.md:225`, the partial-index trick that puts the NULL on the *deleted* side precisely
because SQL treats NULLs as distinct).

rejected the build** — a card takes at most two plain paragraphs. Merged back into one; no card
restructured.

The card's own premise is leveled compaction. Under leveled, write amp goes as `T·log_T(N/M)` and

Replaced with the correct lever from that drill, carrying its numbers and its honest cost (more
levels to probe, space amp ~T/(T-1)). The adjacent "less write-heavy **strategy**" clause was
already correct and is untouched.
