## Sub-scope A -- the campaign's presentation debt

### P2-5 -- the prompt/recall pair becomes a pair

**Where:** `src/scripts/app/content-sheet.js` (`.cs-cue`), `src/scripts/app/cram-derive.js` (`_csCueLine`).

`cram-derive.js:69-72` states the artifact's own contract -- the sheet is read five minutes before a
loop with zero repair context, so *"a prompt -> recall pair both stands alone AND rehearses better
than a bare spine line"*. You rehearse by covering the answer. That was impossible: `.cs-cue`
computed `display:inline` at weight 400, byte-identical to the answer's size and weight, separated
only by a 2.41:1 colour step. Cue and answer were one wrapped paragraph with **no edge to cover**.

```
-.cs-cue{color:var(--mut2)}
+.cs-cue{display:block;font-weight:var(--font-weight-bold);color:var(--mut2)}

-return '<span class="cs-cue">' + c + '</span><span class="cs-arr">&rarr;</span>' + a;
+return '<span class="cs-cue">' + c + '</span> ' + a;
```

The arrow still renders in `.cs-dec`'s "A -> B when ..." below, which IS an inline relation. Here it
announced a *continuation* on the one composition in the file whose contract is that the two halves
**separate**.

**The height cost, stated rather than buried.** A block cue takes its own line, so sheets get taller:

| topic | before | after | screens |
|---|---|---|---|
| content-pipeline *(the spec)* | 3101px | 3194px (+3.0%) | 4.41 -> 4.54 |
| sharding-strategies | 6679px | 6749px | 9.50 -> 9.60 |
| consistency-models *(corpus max)* | 7724px | 7793px | 10.99 -> 11.09 |
| corpus p50 | 5325px | 5442px (+2.2%) | |

That is the honest price of the structural fix: ~2-3% more scrolling, in exchange for a pair that is
coverable on all 46 topics. The volume half of P2-5 is addressed by a **ceiling** instead (below).

**The mirror in `test/cram_surface.cjs` follows the composer** (separator is now a space, not an
arrow). That edit is load-bearing and was **proven** so rather than assumed: desyncing the mirror by
that one glyph fails guard 4 on **all 415 steps**. The literal space in `_csCueLine` is deliberate --
`.cs-cue` is `display:block`, so it collapses to nothing on screen but survives in `textContent`,
which is what `cram_surface.cjs`, copy-paste and every text extraction of this sheet read.

### THE `.a` SLICE IS DECLINED -- and this is the operator's to overturn

The audit offered "slice `.a` to its first sentence (the full text is one tab away in the
whiteboard)". It is the most taste-loaded call in the campaign, so it was **measured before being
judged**, with a candidate slicer over all 415 authored answers:

| | |
|---|---|
| answers the slice CHANGES | **366 of 415** (88%) |
| authored spine text removed | **130,801 -> 47,484 chars (64%)** |
| answers GUTTED to under 25% of their length | **122 of 366**, across **37 of 46 topics** |
| answers the slice cannot shorten (single-sentence) | 49 (13%) |

The corpus is **verdict-then-elaborate**, so the surviving sentence is frequently a bare verdict
whose entire teaching value lived in the dropped text:

```
  1% kept   301 ->   3ch   consistent-hashing[6]    "No."
  2% kept   466 ->  11ch   error-propagation[8]     "Additively."
  3% kept   268 ->   9ch   idempotency[5]           "It races."
  3% kept   629 ->  22ch   sharding-strategies[5]   "Underneath each shard."
  4% kept   907 ->  34ch   consistency-models[5]    "Draw two arrows and one non-arrow."
```

It is also **uneven by construction**: a 353-char single-sentence answer survives whole while a
907-char step collapses to 34 chars. A volume fix whose effect does not correlate with volume is not
a volume fix.

And it could not ship as-is anyway: `cram_surface.cjs`'s STRING COVERAGE guard asserts the full
`wb.steps[].a` text appears in the rendered sheet, so slicing trips mirror drift on every step. The
slice would require weakening the check that guards this exact surface.

> **Two hypotheses were tested and DISPROVED rather than reported.** I first believed the survivors
> were whiteboard stage directions ("Draw...", "Sketch...") -- measured, only **3%**. I then believed
> the slice would re-create the `dangling` defect class; run against the repo's own `RE_PRONOUN` /
> `RE_ELLIPTIC` detectors it creates **zero** net-new dangling answers, because it cuts the tail, not
> the head. Both are recorded because a reader deserves to know which of my claims survived contact
> with a measurement. The case against the slice rests solely on the gutting number, which is enough.

**If the operator wants it anyway,** it is one function (`_csCueLine`) plus a mirror update, and the
worst cases above are the list to review first.

### G-switcher + G-nav-fold -- `test/sidebar_geometry.cjs`

Both defects were invisible to the entire existing gate **by construction**: the controls work, so no
behaviour check moves, and VR captures the sidebar at rest where a clipped switcher looks like a
deliberately short label. What was wrong is how much of each you could SEE.

**WATCHED-RED:** 11 of 13 assertions FAIL on the committed pre-fix deliverable (18px switcher at all
five desktop widths; 4 of 9 tabs above the fold); 13 of 13 PASS here.

**Thresholds anchored on two measured populations, all 46 topics at 1280px:**

| | ratio | clientWidth |
|---|---|---|
| pre-fix | 0.063 .. 0.243 | 18px on every topic |
| fixed | 0.365 .. 1.000 | 103px on every topic |
| threshold | **MIN_RATIO 0.30** | **MIN_PX 60** |

Nothing lies in 0.243 .. 0.365, so any line in that gap separates them; 0.30 is 23% clear of the
pre-fix best case and 18% clear of the fixed worst case ("Production Debugging and Incident
Diagnosis", 103/282). It is deliberately **not** pinned to 0.365, today's floor -- a guard set at the
observed worst case fails the first time someone writes a longer title, which is authoring, not
regression. The **px arm** exists because the ratio conflates box width with name length;
`clientWidth` is name-independent (one constant across all 46, before and after), so it still holds if
a future title drags the ratio down.

> My first draft set `MIN_RATIO` to 0.40 from a **single topic's** reading and **would have failed the
> very build it ships with** (the real floor is 0.365). Measuring all 46 is what caught it. A
> threshold picked from one sample is a threshold picked from air.

`MIN_TABS = 7` is the audit's own line, counted the audit's own way (a tab with any part above the
fold -- which is what its "Visible: walk, drill, wb, sys" = 4 counted). The stricter fully-above count
is **reported beside it, deliberately unasserted**, for the 3px reason above.

**Both arms run a negative control every invocation** and the check ABORTS rather than report a green
it did not earn. The fold control had a real bug on first write: deriving its shift from `MIN_TABS`
made it **negative** on the pre-fix build (-52px), which moved the fold DOWN, raised the count 4 -> 5
and failed the control for a reason that had nothing to do with the app. It now anchors on the last
tab this build actually shows, +2px for the rounded-vs-float top. A control that misfires on the very
build it is meant to catch is worse than no control.

### G-cram-height -- new arm in `test/cram_surface.cjs`

Everything else in that file reads the sheet as TEXT; this renders it at a pinned 1280x800 and
measures how tall it is.

```
corpus, post-fix:  min 3194   p50 5442   p90 6462   max 7793 (consistency-models)
CEILING = 9000  =  max x 1.155
```

The headroom is sized on a **real event**, not a round number: a topic gaining a TENTH authored
whiteboard step grows its sheet by about 1/9 = 11%, and that is authoring, not regression -- so the
worst topic in the corpus can take one more step and still pass. A structural regression is far larger
than 15% and trips immediately.

**No natural red exists** (the pre-fix max was 7724, also under), so the watched-red is a **plant**,
via the file's existing `--plant` mechanism: doubling `consistency-models`' authored steps takes it to
**10661px / 15.2 screens** and the arm reports it 1661px over. Plus a per-run **negative control** -- a
400px block appended to the rendered sheet must raise the measured height, or the probe is not reading
the live node and the check aborts.

It is a **ceiling, not a target**: this wave did not shrink the corpus. It stops the number getting
worse unnoticed, which nothing did before.

## The gate reached 67/67 -- through one unrelated defect, diagnosed rather than re-rolled

The re-gate did **not** come back green on the first try. `overlay_deadzone` -- a check this wave

**It was proven not to be this wave's regression before a line was changed:**

| evidence | |
|---|---|
| deliverable across every run | **byte-identical**, md5 `5d868341` |
| in-gate at `9aef376` | **PASS**, 35 assertions |
| in-gate, twice after | **FAIL**, 60s timeout at `:106` |
| standalone, the gate's exact argv | **PASS 3/3** |
| orphaned Playwright browsers / CPU | **0** / 10% |

A check that passes 3/3 alone and fails under gate concurrency is a frame-scheduling race -- and
this wave's changes were present in the passing run too.

**Root cause, read from the source rather than guessed.** The rAF poller installed at
`document_start` ended only on *"splash exists AND carries `_bs-done`"*. If the splash is REMOVED
before any frame catches that class, `sp` is null on every later tick, `window.__fading` never flips,
and the `waitForFunction` burns its full 60s. The removed-splash case is the one the comment eight
lines below **already calls "a pass by construction"** -- the wait simply could not reach it.

The fix adds a second exit (splash absent and `document.readyState === 'complete'`). An element not
in the DOM cannot hit-test, so the assertion it skips is vacuous; the original branch is untouched
wherever the splash IS present. It widens the exit, it does not weaken the assertion -- the check
still makes all **35** of its assertions.

> the deliverable md5 is unchanged). The ruling says no new scope; this is not product scope, it is
