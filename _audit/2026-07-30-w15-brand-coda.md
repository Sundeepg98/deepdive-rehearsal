## What and why

W3 gave the home hero the room of the topic it opens. It left the brand mark alone, by scope, and
flagged the consequence: on a cold home `.hm-brand` wore **architecture-apis magenta** -- not
because the app was in that room, but because `src/index.html:2` hard-codes `data-group` for first
paint and `applyIdentity` deliberately does not run at boot. On a topic-less route that accent is a
**boot constant**. So the first screen carried two real room colours 130px apart and only one of
them meant anything.

Ruling (team-lead, operator-delegated): on the home route the brand mark wears the **brand indigo**.
Brand claims brand; nothing on the first screen accidentally claims a room.

## The change -- one selector, added to a rule that already existed

```
-.ix-panel,.xd-panel,#_search-overlay,.tn-menu{
+.ix-panel,.xd-panel,#_search-overlay,.tn-menu,#home .hm-brand{
       --topic-ink:#534AB7; ... --acc:var(--topic-ink); ...

-html[data-theme="dark"] .ix-panel, ... ,html[data-theme="dark"] .tn-menu{
+html[data-theme="dark"] .ix-panel, ... ,html[data-theme="dark"] #home .hm-brand{
       --topic-ink:#9D93F0; ...
```

`.hm-brand` already declared `color:var(--acc)`, so **no declaration was added or changed** -- the
element joins the block that supplies `--acc`, and the existing declaration does the rest.

### Why this source, verified on disk before use

The brief said to bind a token if the favicon/badge derive from one, and to mirror the badge if only
literals exist. What is actually on disk:

| source | value | how |
|---|---|---|
| favicon (`index.html:7`, base64 SVG) | `#534AB7` | hardcoded `fill="#534AB7"` in the data URI -- unavoidable, it is an embedded asset |
| badge (`tw.css:40`) | `#534AB7` | `linear-gradient(135deg, var(--color-acc) ...)`; `--color-acc:#534AB7` at `tw.css:17` |
| roomless default (`styles.css:187`) | `#534AB7` | the bare `html{}` rule in THE SIX ROOMS, before any `data-group` |
| `.ix-panel` neutralisation | `#534AB7` / `#9D93F0` | **the only construct carrying the pair in BOTH themes** |

The `--indigo` token was checked and **rejected**: it is `#4338CA` light / `#9D93F0` dark, so its
light value is not the brand indigo at all -- it is a verdict hue, and binding it would have shipped
a colour the favicon and badge do not use. `--color-acc` is the badge's own token but has no dark
variant (the badge keeps one gradient in both themes and flips only its ink), so it cannot serve a
text mark that must stay legible on a dark background.

That leaves the neutralisation block, and its own comment already names it:

> "The neutral is the app's **BRAND indigo** -- already this codebase's roomless default ... **and
> the badge colour**. It is not one of the six rooms and, the whole point, **IT DOES NOT MOVE**."

So the change adds **zero new literals**: it reuses the exact pair the codebase already calls the
brand indigo, in the one place that carries it theme-aware.

**The block's membership rule was widened honestly, not quietly.** Its comment said "a cross-group
surface is any surface that ENUMERATES OR ACTS ACROSS ROOMS", and the brand mark does no such thing.
The comment now reads the rule as **"must not claim a room"** -- what all five members share --
with the first four there because they list all rooms and `.hm-brand` there because it names the
product, not a topic. It is written as the explicit mirror of the block's existing exclusion:
`.tn-trigger` wears the current room *because* it names the current topic.

**Scoping.** `#home .hm-brand` -- the same `#home ...` idiom the home block already uses for
`#home .ix-panel`. The topic route is untouched: `.hm-brand` exists only inside `#home`, and the
14 non-home baselines are byte-identical (below).

## The assertion

Added as **arm 3 of `test/room_browser.cjs`** -- not a new check. That file already owns the
question "what wears which room, wired at boot", and this is that system's deliberate exception, so
it is the honest home rather than a forced one. **The gate stays at 67 rows**, with `room_browser`
now carrying five assertions instead of two.

It asserts two things, in both themes, on the home route:

1. `.hm-brand`'s computed colour **equals the brand indigo**, read LIVE off the `.ix-panel`
   neutralisation on the same page.
2. `.hm-brand`'s computed colour **matches none of the six room inks**, read from `--room-*`.

**No hex is hardcoded in the test.** Both references are resolved through a hidden probe element so
a token's hex and a computed `rgb()` compare equal. Arm 2 is the load-bearing one: it states the
property that actually matters -- *no element on the first screen accidentally claims a room* -- and
it keeps holding if every hex in the palette changes. Arm 1 would still pass if the brand and the
neutral drifted together, which is why arm 2 exists.

**Watched red on the pre-fix build** (capture: `_audit/w15-brand-before-after/watched-red-room-browser.txt`),
exit 1, four failures -- both arms, both themes, and it names the cause:

```
- [light/home] .hm-brand is rgb(150, 61, 134), not the brand indigo rgb(83, 74, 183)
               that the .ix-panel neutralisation carries
- [light/home] .hm-brand (rgb(150, 61, 134)) is room ink for [architecture-apis] --
               the brand mark must claim NO room (this is the boot constant from
               index.html, which means nothing on a topic-less route)
- [dark/home]  ... rgb(218, 141, 202) ... [architecture-apis] ...
```

Green after the change, same command, exit 0.
