## Item 1 -- `cdc`'s 9-line tell: the DEFECT DOES NOT EXIST, and the instrument that reported it is fixed

### What the brief asked, and why it is not the right action

W4's P3-4 recorded an honest exception: under the medium weight, `cdc`'s third `.dec-tell` went
7 -> 9 lines, "a narrower weight rebreaks its words into a worse ragged edge". The brief asked for
the smallest honest content-shape intervention to bring it back to <= 7 lines.

**Reproduced first, per the brief. The block is FIVE lines.**

| measurement, 1280x800, deliverable committed at `96deb28` | |
|---|---|
| `.dec-tell` box height | 121.4px |
| `clientHeight` / `scrollHeight` | 120 / **120** -- equal, so nothing overflows |
| `padding-top` / `line-height` | 12px / 21.7px |
| content height | 120 - 12 = 108px |
| **108 / 21.7** | **4.98 -> 5 line boxes** |
| computed `overflow` / `max-height` | `visible` / `none` |

A block's height IS its stacked line boxes. 108px of 21.7px line boxes is five lines, `scrollHeight
== clientHeight` proves no content is hidden, and `overflow:visible` with `max-height:none` proves
nothing is clipped. Nine lines would be 208px. **The rendering does not contain the defect.**

The rendered receipt is committed at `_audit/w23-receipts/cdc-tell3-1280x800.png` (1280x800, dsf 2,
the tell's own box plus 14px) so the five lines can be counted by eye rather than taken on trust.

### Where the 9 came from: the census counts rect fragments, not lines

`_audit/2026-07-29-w4-census.cjs` counted **distinct rounded rect tops** of a `Range` over the
element. That over-counts any block holding an inline `<code>`: the code span carries its own
font-size (11px) and line-height (17.05px) inside 14px/21.7px prose, plus `1px 5px` of padding, so
`getClientRects()` emits its fragments at tops that are neither the line tops nor a line-height
apart. Measured on `cdc`'s third tell, relative to the block top:

```
rect tops:  14, 18, 19, 35.69, 39.69, 40.69, 57.38, 79.06, 100.75   -> 9 distinct tops
line tops:  14,         35.69,               57.38, 79.06, 100.75   -> 5 lines, 21.7px apart
            (18/19 and 39.69/40.69 are the code span's own fragments, sitting ON lines 1 and 2)
```

**The correlation over the whole corpus is a clean double implication, not a hint.** Comparing the
census counter against the block-height counter on all 324 `.dec-tell` in 46 topics:

| | |
|---|---|
| tells measured | 324 |
| the two methods agree | 296 |
| **they disagree** | **28** |
| of those 28, how many contain an inline `<code>` | **28** |
| tells containing an inline `<code>` | **28** |
| of those, how many the old counter got right | **0** |

Every disagreement has a code span; every code span produces a disagreement; nothing else disagrees.
Corpus total moves **1532 -> 1435 lines** for the same 324 blocks.

### What that means for the W4 record, stated precisely

The W4 freeze's `.dec-tell` table is **not** wholesale wrong, and this report will not overclaim.
Both sides of its before/after were measured with the same counter, so its *deltas* on tells without
code are sound -- and the corrected counter reproduces its two headline rows **exactly**:

| topic | W4 recorded (post-fix) | corrected counter, today |
|---|---|---|
| `content-pipeline` (the spec) | `[1,1,1,1,2,1,2]` | **`[1,1,1,1,2,1,2]`** |
| `multi-region` (the audit's worst case) | `[5,5,6,9,6,5,5]` | **`[5,5,6,9,6,5,5]`** |
| `cdc` | third tell "9" | **`[5,5,5,5,5,5,4]`** |

The correction is surgical: it moves the 28 code-bearing tells and nothing else. What does NOT
survive is the absolute total (1577 -> 1532 was inflated on both sides) and the `cdc` exception,
which was an artifact of the one tell in that topic that carries a code span.

**The corpus maximum is still 9** (`multi-region`'s fourth tell), by both methods. The corrected
counter did not floor everything to five; it still reports a genuinely long block as long. That is
the discrimination proof.

### Disposition: DECLINE the content edit, FIX the instrument

Editing authored prose to move a number produced by a broken counter is the Goodhart move this
project's guards exist to prevent -- the same call W4 made on the 3px shave and the team-lead
ratified. The tell is already inside the brief's own acceptance criterion (5 <= 7) when measured
correctly. **No content was touched, in `cdc` or anywhere else.**

`_audit/2026-07-29-w4-census.cjs` is corrected instead, in both of its `lineCount` copies (they run
in separate `page.evaluate` calls and cannot share a closure): rect tops are now clustered into line
boxes using the element's own line-height, with a half-line-box quantum and a 4px fallback for
`line-height:normal`.

**And it now carries the control that would have caught this.** `MEASURE_TELL` computes a second,
mechanically independent count -- `(clientHeight - padding) / line-height`, arrived at through the
box model rather than through Range rects -- and the runner **aborts the whole census** if the two
ever disagree on any of the 324 blocks, rather than printing a line count someone will quote in a
freeze report. On this build it reports `0 disagreement(s)`.

**One honest observation, since I looked at the pixels.** The code span `WHERE published = false`
does wrap across lines 1 and 2. That is ordinary inline wrapping, both fragments are legible against
their shared background, and it is not the recorded defect. Forcing it unbroken would be a style
rule (which the brief forbids) and would push the block to six lines -- making it longer to fix a
nit. Left alone, deliberately.

### 2. The named headroom does not exist, and never did

W4's next-pass note 3 says "real headroom exists in `.side-id` (the `.sub` paragraph and `.kbd-hint`

### 3. What is left is load-bearing, and one part of it is guarded against exactly this

So the reclaim is: delete real chrome, or re-open a fixed accessibility-adjacent bug, to move a
threshold. That is the Goodhart move W4 refused and the team-lead ratified ("the 3px `num` shortfall
was not revisited -- the Goodhart refusal stands as recorded"). **It stands, on stronger evidence.**

### The widening found a live escapee on its first run

```
ROOM STATIC: FAIL
  - 1 hardcoded indigo literal(s) regrew -- use an --acc-aNN rung, or
    color-mix(in srgb, var(--color-acc) N%, transparent) for a brand-fixed rung
  -   at src/tw.css:49  rgba(83, 74, 183
```

`src/tw.css:49`, `.badge`'s own `box-shadow`, carried `rgba(83, 74, 183, .2)` -- the retired indigo
in the spaced notation, i.e. the literal digits of the **same token the rule's own `background` uses
by name two declarations above**. The codemod had regrown, in exactly the form the old pattern could
not see. It is live: `.side-id .badge` ("Deep rehearsal") paints it on every topic route.

**Closed, at zero pixels:**

```css
box-shadow: var(--chip-sh), 0 0 20px -4px color-mix(in srgb, var(--color-acc) 20%, transparent);
```

Identity, verified rather than argued -- computed on the badge before and after:

```
BEFORE  rgba(83, 74, 183, 0.2)
AFTER   color(srgb 0.32549 0.290196 0.717647 / 0.2)
        0.32549*255 = 83   0.290196*255 = 74   0.717647*255 = 183   alpha .2
```

Same colour; only Chromium's serialization notation changed (the other two shadows on this element
already serialize that way -- they are `--acc-a08`/`--acc-a12`, which are color-mix rungs). VR
confirms it: **0 changed pixels on all 16**. Brand-fixed on purpose, not an `--acc-aNN` rung: this
chip does not retint per room, and its gradient is `--color-acc` too.

### Hex is deliberately NOT matched, and the residual is recorded rather than hidden

H-1's table lists hex as a missed notation. Matching it would be wrong here, and the reason is in
the tree: `#534AB7` is the palette's **own definition notation** (`styles.css:200`, `:1564`,
`tw.css:17`) and -- per W20 section 7.1's own resolution -- the sanctioned way to name this colour in
prose. A hex rule would fail the tree on its own token declarations.

So the gap this leaves is stated, not papered over: **a hex literal in a CONSUMER position is still
invisible to rule 1**, and `src/scripts/app/print-qa.js:15,17` carry one today (`color:#534AB7` in
the print QA sheet). Not touched -- deciding whether the print sheet should wear brand indigo is a
design call with its own rebaseline, not an S-wave's. **Recorded here and in the check's own comment
so it is a known gap rather than a covered one.**
